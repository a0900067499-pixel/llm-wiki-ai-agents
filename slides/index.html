觀眾設定：有一點程式基礎。

從管家 Alfred 說起

你對 Alfred 說：「我想喝咖啡。」

聽懂、規劃

去廚房 → 用咖啡機 → 煮 → 端回來。

使用工具

他知道有咖啡機可以用，就去用它。

完成目標

把咖啡交到你手上。

Alfred 有「代理能力」（agency），因為他能改變周遭的環境，而不只是說話。

Agent 的定義

兩種說法

  • 課程版：用 AI 模型和環境互動、去達成使用者目標的系統，結合推理、規劃與行動，通常透過外部工具。
  • 工程版：LLM 的輸出控制了程式的流程。

關鍵特徵：LLM 自己管理流程、判斷何時完成、修正動作，失敗時能停下來把控制權交還給你。

這些「不是」agent

  • 單純的聊天機器人
  • 單次 LLM 呼叫
  • 情緒分類器

它們都用了 LLM，但 LLM 沒有決定接下來要做什麼。

大腦，加上四樣配備

LLM 是 agent 的大腦。但只有大腦不夠，還需要：

規劃

把大任務拆成小步驟，一步一步想；做完再檢查、修正。

記憶

短期：context window（AI 當下能同時讀進的內容量，有上限）。
長期：向量資料庫（外接的筆記本，需要時再查）。

工具

LLM 只能產生文字。要寄信、生圖，都得透過外部的功能。

規範

Instructions：告訴 agent 該怎麼做、哪些不能做的準則。

注意：LLM 不一定會正確使用工具，例如給錯輸入值。

工具分成三類

類型用途例子
資料類（查資料）取得完成任務需要的資訊查資料庫、讀 PDF、搜尋網路
行動類（做動作）改變外部系統寄信、更新紀錄、轉交真人
協調類（請別人做）把其他 agent 當工具使用退款 agent、研究 agent

各家叫法不同：OpenAI 說 Model＋Tools＋Instructions，Anthropic 說「增強版 LLM」，指的都是上一張那一套。

是不是 agent？是程度問題

程度名稱LLM 的輸出控制了什麼程式長相
☆☆☆Simple processor不影響流程process_llm_output(resp)
★☆☆Router一個 if/else 分支if llm_decision(): path_a()
★★☆Tool call要執行哪個函式run_function(tool, args)
★★☆Multi-step agent要不要繼續下一輪while llm_should_continue(): ...
★★★Multi-agent一個 agent 啟動另一個if llm_trigger(): execute_agent()

Wiki 註記：HF 課程把 Multi-step agent 標成 ★★★，但原始出處 smolagents 標 ★★☆。本表以原始出處為準。

ReAct：想一下、做一下、看結果

以前的研究常把「推理」和「行動」分開。ReAct 讓兩者交錯進行：

  • Thought：建立、追蹤、更新計畫，處理例外
  • Action：呼叫工具，向外部取得資訊
  • Observation：讀取工具結果，再進入下一輪

效果

  • 問答與事實查核：用簡單的 Wikipedia API 查資料，減少幻覺與錯誤累積。
  • 兩個互動任務（文字遊戲、網頁操作）：只給一兩個示範，成功率就比需要另外訓練的方法高出 34%／10%。

把迴圈寫成程式

memory = [user_defined_task]
while llm_should_continue(memory):
    # Thought：LLM 先推理，再決定 action
    action = llm_get_next_action(memory)
    observations = execute_action(action)
    memory += [action, observations]

迴圈什麼時候停？呼叫了「最終輸出」工具、回覆時不再呼叫工具、發生錯誤，或達到最大回合數。

memory（按「執行下一步」看它怎麼長大）

示意：程式出自 smolagents，註解是補充說明；沿用 Alfred 煮咖啡的例子，觀察結果是為了說明而編寫的。

Workflow 還是 Agent？

Workflow

用預先寫好的程式路徑編排 LLM 與工具。適合定義清楚、需要可預測的任務。

衝浪旅行社：顧客只想查行程或找業務 → 一個搜尋框加一個聯絡表單就夠。

Agent

讓 LLM 自己動態決定流程與工具。適合需要彈性的情境。

衝浪旅行社：「週一到，但忘了護照可能延到週三，能不能週二早上去衝浪、還要取消險？」→ 需要天氣、地圖、排班表、知識庫一起判斷。

判斷法則：預先寫好的流程太常不夠用時，才需要 agent 的彈性。

何時該用 agent？

先選最簡單的

  • agentic 系統是用「更慢、更貴」換「表現更好」
  • 很多應用只要把單次 LLM 呼叫優化好就夠
  • 流程可預測，就直接寫死，最可靠

三個「該用」的訊號

  • 複雜決策：例如退款審核
  • 難維護的規則：例如供應商資安審查
  • 大量非結構化資料：例如房屋保險理賠

比喻：規則引擎像核對清單，agent 像資深調查員，讀得出細微的脈絡。

五種設計模式，由簡到繁

這五種都屬於 workflow：流程由程式事先寫好。

模式做法例子
1Prompt chaining 步驟串接固定步驟串接，中間加檢查關卡寫大綱 → 檢查 → 寫全文
2Routing 分流路由先分類，再送到專門流程客服分成一般、退款、技術
3Parallelization 平行處理子任務同時跑，或同題多跑投票多個 prompt 檢查程式漏洞
4Orchestrator-workers 指揮者與工人指揮者在執行時拆任務、分派、彙整一次修改很多檔案
5Evaluator-optimizer 評估者與優化者一個產生、一個評估，反覆改進文學翻譯、多輪搜尋

這份簡報本身就是用「chaining ＋ 檢查關卡」和「evaluator-optimizer」做出來的，詳見流程說明頁。

什麼時候拆成多個 agent？

先把單一 agent 用到極限，多 agent 會增加複雜度。拆分的訊號是提示詞邏輯太複雜，或工具太多又彼此重疊。

Manager 模式

經理 agent 把專門 agent 當工具呼叫，自己負責跟使用者對話。

例：翻譯經理呼叫西語、法語、義語 agent。

Handoff 模式

同儕 agent 之間轉交控制權。

例：分診 agent 轉給技術支援、業務、訂單管理。

工具數量沒有固定上限：有的系統能處理 15 個以上不同工具，有的在不到 10 個重疊工具時就出錯。

護欄與人工介入

多層護欄，一層擋不住還有下一層

  • 相關性分類器：擋離題問題
  • 安全分類器：偵測越獄（用話術誘導 AI 違規）、提示詞注入（把惡意指令藏在輸入裡）
  • 個資過濾、內容審核
  • 工具風險分級：看讀或寫、能否復原、金錢影響
  • 規則式防護：黑名單、長度限制、格式比對

什麼時候要找真人

  • 超過失敗門檻：例如多次聽不懂顧客意圖
  • 高風險動作：取消訂單、大額退款、付款

自主 agent 錯誤會累積，應先在沙盒（和真實系統隔離的測試環境）中充分測試。

Agent 的弱點

  • context 有限：歷史、指令、工具說明都要塞進去
  • 長期規劃困難：長任務遇到意外錯誤時很難調整
  • 輸出格式不可靠：所以很多程式碼在做解析
  • 錯誤會累積：每一步的小錯一路放大

LLM 不一定能評估自己

ChemCrow（加了 13 個化學專業工具的 agent）：LLM 評審認為它和 GPT-4 差不多，但化學專家明顯偏好 ChemCrow。

把工具設計得防呆（不容易用錯）

要求工具一律給完整的檔案路徑、而不是相對位置，就消除了 agent 切換資料夾後走錯路的錯誤。
