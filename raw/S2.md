- Definition: AI agents are programs where LLM outputs control the workflow.
- Agency is not binary; it is a continuous spectrum depending on how much power the LLM has over the workflow.
- Agency levels table:
  - ☆☆☆ Simple processor — LLM output has no impact on program flow — `process_llm_output(llm_response)`
  - ★☆☆ Router — LLM output controls an if/else switch — `if llm_decision(): path_a() else: path_b()`
  - ★★☆ Tool call — LLM output controls function execution — `run_function(llm_chosen_tool, llm_chosen_args)`
  - ★★☆ Multi-step Agent — LLM output controls iteration and program continuation — `while llm_should_continue(): execute_next_step()`
  - ★★★ Multi-Agent — one agentic workflow can start another — `if llm_trigger(): execute_agent()`
  - ★★★ Code Agents — LLM acts in code, can define its own tools / start other agents
- Multi-step loop:
  ```
  memory = [user_defined_task]
  while llm_should_continue(memory):
      action = llm_get_next_action(memory)
      observations = execute_action(action)
      memory += [action, observations]
  ```
- When to avoid: agents are often overkill; if workflow is predictable, code it deterministically for a fully reliable system.
- Surf trip example: "trip knowledge" vs "talk to sales" → fixed workflow (search bar / contact form) is enough. A complex request (Monday, forgot passport, maybe Wednesday, surf Tuesday morning with cancellation insurance) needs a multi-step agent with weather API, maps API, staff availability dashboard, RAG over knowledge base.
- Rule: if the predetermined workflow falls short too often, you need more flexibility.
- Framework needs once you have tool calling / multi-step loop: output parsing, memory, error handling (logging and retries). Core components: LLM engine, tool list, system prompt (ReAct: Reflection → Action → Observation), parser, memory.
- Code agents vs JSON tool calling: code is more composable, can store objects in variables, more general, well represented in training data.
